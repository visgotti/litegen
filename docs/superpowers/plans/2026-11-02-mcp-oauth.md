# LiteGen MCP OAuth, dashboard pages and OAuth client guides (plan 2 of 2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. The user chose native execution with no subagents (2026-11-02). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let ChatGPT, claude.ai, Claude Desktop and any OAuth-capable client connect to LiteGen's MCP endpoints by signing in. Each connection acts as the approving user, narrowed to the scopes they approve. Add the dashboard's consent and "Connect AI tools" pages, and finish the client guides.

**Architecture:** LiteGen becomes its own OAuth 2.1 authorization server for its two MCP resources (`src/mcp/oauth/`). It serves discovery documents, client registration (CIMD first, DCR as fallback), authorization with a dashboard consent page, and a token endpoint that issues opaque, hashed, endpoint-bound tokens. The MCP auth layer from plan 1 resolves those tokens to a session-like `KeyContext` for the user. Tool calls pass that context to the API router as a request extension, so handlers apply the user's own role checks.

**Tech Stack:** Rust (axum 0.8, sqlx SQLite + Postgres, rmcp 3.8), React 19 + react-router 7 + Vite (dashboard), `@litegen/sdk` (TS) and `litegen` (Python) SDKs, Playwright, Node 24 + `@modelcontextprotocol/sdk`.

**Spec:** `docs/superpowers/specs/2026-11-02-mcp-server-design.md` (section "OAuth 2.1 for MCP"). Builds on plan 1, `docs/superpowers/plans/2026-11-02-mcp-server.md`, which must be complete. Client requirements: `docs/superpowers/research/2026-11-02-mcp-clients.md`.

## Global Constraints

- Everything in plan 1's Global Constraints applies.
- OAuth scopes are exactly `ai:generate`, `ai:read`, `admin:read` and `admin:write`. They map to `Scope::Generate`, `Scope::Read`, `Scope::Read` and `Scope::Admin` on `/mcp`, `/mcp`, `/admin/mcp` and `/admin/mcp` respectively.
- Tokens are opaque: `lgat_` (access) or `lgrt_` (refresh) followed by 43 base64url characters from 32 random bytes. Only their SHA-256 hex is stored. Access lives 3600 s and refresh 30 days (`mcp.oauth.*_ttl_*`).
- Authorization codes: 32 random bytes, stored hashed, valid 60 s, single use. Pending authorization requests are valid 10 minutes.
- PKCE `S256` is required. `plain` and a missing challenge are refused.
- Every redirect to a client carries `iss` = the issuer (RFC 9207), errors included.
- The token endpoint takes `application/x-www-form-urlencoded`, answers `Cache-Control: no-store`, and uses RFC 6749 error JSON.
- Issuer = `server.public_base_url` (no trailing slash). Discovery documents are only served when `mcp.oauth.enabled`.
- OAuth access tokens authenticate only on `/mcp` or `/admin/mcp` (whichever their grant names), never on the REST API.
- Every new REST endpoint is in `/openapi.json`, has a TS SDK method and a Python SDK method (the contract tests stay green without growing `sdks/contract-allowlist.json`), and is either an MCP tool or in `EXCLUDED` with a reason.
- Before landing the OpenAPI change, tell the user that the frontend/SDK session needs to know (shared-tree rule). Regenerate with `sdks/scripts/regen-all.sh` in the worktree.
- New migrations are `20240101000017_mcp_oauth.sql` in both `migrations/sqlite` and `migrations/postgres`. If a `…017_` exists on `3d-models` when this lands, use the next free number in both.

## Review Focus

1. **Redirect-URI handling.** An unknown client or unregistered `redirect_uri` must get an error page from LiteGen, never a redirect to the unverified URI. Loopback URIs match any port, but only for `localhost`, `127.0.0.1` and `[::1]` over `http`. Test in Task 3 and Task 4.
2. **Scope escalation through consent.** A Member (no `KeyWriteAny`) approving `admin:write`, or a Viewer (no `GenerationCreate`) approving `ai:generate`, must be refused at approve time, even when the client requested it. Test in Task 4.
3. **A token used where it does not belong.** An `/mcp` token on `/admin/mcp` or on `/v1/models` must get 401 `invalid_token`. A token whose user was removed from the org or deactivated must get 401. A revoked grant's tokens must stop working on the next call. Test in Task 6.
4. **Replayed codes and refresh tokens.** A second use of an authorization code, or of a rotated refresh token, revokes the whole grant. Test in Task 5.
5. **Discovery behind the `/api` prefix.** A client deriving well-known URLs from `https://host/api/mcp` must find the documents at `/.well-known/oauth-protected-resource/api/mcp` and `/.well-known/oauth-authorization-server/api` as well as under `/api/.well-known/…`. Test in Task 2. The Caddyfile is changed to match.
